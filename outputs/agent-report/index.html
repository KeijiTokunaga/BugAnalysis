01 / WHY

修正できても、原因の理解が残らない。

原因がラベルで止まる

「条件分岐の漏れ」「確認不足」は現象の説明に近く、なぜその実装になったかが抜け落ちます。

後からの解釈に偏る

現在の仕様や修正後の理解で振り返ると、当時は分からなかったことまで「知っていたはず」と扱いがちです。

記録が改善につながらない

「レビューを徹底する」だけでは、何を変えると再発や流出を防げるかが具体化しません。

基本姿勢：非難ではなく、学習。

問うのは「誰が間違えたか」ではなく、「どの情報と条件の下で、その判断が成立したか」。個人の評価に直結させず、システムとプロセスの改善に使います。

02 / CONCEPT

証拠を読み、問いを絞り、説明を一緒に作る。

READ

事実を整理する

不具合票、当時の仕様、修正差分、関連コード、テスト結果から、分かることと分からないことを整理します。

ASK

判断の背景を聞く

実装時の前提、仕様の曖昧さ、設計の迷い、時間や環境の制約を、回答を誘導せず一問ずつ確認します。

CONNECT

改善につなげる

発生の仕組みと検知できなかった理由を分け、根拠付きの分析案と、検証可能な対策を作ります。

AIは原因の認定者ではなく、分析と対話の支援者です。開発者の内心を推定して事実扱いせず、本人への確認と資料の裏付けを分けます。

03 / WORKFLOW

開発者の修正に、AIの対話と記録を重ねる。

開発者の追加作業は、主に「当時の認識に答える」「分析案を訂正・確認する」ことです。AIが資料の整理と文章化を支え、品質担当者が改善の実行と効果確認につなげます。

一つの不具合で残る成果物
根拠付き分析記録（直接原因・流入・背景・流出）＋未確認事項＋対策（担当・期限・効果確認方法）。修正完了と改善策の完了は別々に管理します。
04 / CONVERSATION

同じ「分岐漏れ」でも、背景は違う。

以下は架空の対話例です。実案件の分析結果ではありません。

開発者

取消済みの注文を処理してしまいました。条件分岐の書き忘れです。

エージェント

差分では取消済みの場合の分岐が追加されています。実装時は、その状態の注文がこの処理に来る可能性をどう理解していましたか？

開発者

呼び出し元で除外されると思っていました。以前の処理がそうだったので。

エージェント

以前の処理を根拠にした前提だったのですね。当時の呼び出し元や仕様で、その前提を確認できる資料はありますか？

開発者

仕様には書かれていませんでした。テストも以前のケースを流用していました。

エージェント

「仕様に記載がない」は当時の版で確認しましょう。テストについては、取消状態を対象に含める判断や、状態一覧との照合があったかを確認できますか？

分析候補：直接原因は取消状態の処理不足。流入の背景には呼び出し元の保証に関する前提、流出には状態別テストの不足が関係する可能性があります。当時の資料を確認するまでは仮説として残します。
05 / QUALITY RECORD

カテゴリを付ける前に、因果と根拠を残す。

分析台帳の中心となる情報
記録項目記録する内容分析の確認点
現象・影響期待、実際、再現条件、重大度、実影響と潜在影響何が、どの条件で、誰に影響したか
直接原因誤動作を起こしたコード・データ・状態の関係現象を技術的に説明できるか
流入誤った前提・仕様・設計・実装が入った工程と版発見工程と混同していないか。不明を許容しているか
背景・寄与要因当時の認識、参照情報、設計の迷い、制約本人の説明と分析側の解釈を分けているか
流出検知できた可能性のある工程、確認範囲、検知を妨げた条件その時点の情報で検知が可能だったか
根拠・不確実性資料の版・参照箇所、発言、検証結果、仮説、未確認事項第三者が根拠を追い、別の説明を検討できるか
対策・効果修正、再発防止、流出防止、担当、期限、確認方法対策が原因と対応し、効果を確かめられるか

原因カテゴリは最後に付け、複数要因を認めます。深い原因を無理に作らず、証拠が支える範囲で止めます。

プロジェクト特性・品質指標とのつながり

不具合IDを機能・要件・リリース・変更IDと関連付け、要件数、総／変更ステップ数、重要度、検証範囲、利用条件を別台帳から参照します。不具合数・テスト失敗数・本番失敗処理数は別に数えます。

品質は件数だけで評価しません。規模に対する発見状況、利用者への影響、検証・観測の範囲を並べます。未計測をゼロとせず、計数定義が異なる製品間の単純な順位付けには使いません。

06 / TRUST

AIの断定を、仕組みで防ぐ。

事実と仮説を分離

資料で確認した事実、本人の説明、AIの仮説、未確認事項を区別。重要な主張には参照先と確認状態を持たせます。

当時の情報で検証

実装当時の仕様・コードを参照。修正差分だけで心理や流入工程を決めず、仮説と矛盾する証拠も探します。

人が訂正・承認

台帳への確定登録は人が確認。異論は記録し、重大案件では別の確認者もレビューします。

話せる範囲を守る

回答を強制せず、閲覧権限・保存期間・利用目的を設定。コード・ログの送信可否を確認し、秘密情報や不要な個人情報を除きます。

07 / PILOT & EVALUATION

「分析が正しそう」ではなく、証拠と実用性で評価する。

まず、共有可能な過去案件を使い、軽微・重大・再発・仕様起因など異なる事例で試行します。対話前後の分析を、可能な範囲で作成方法を伏せて、開発・品質の確認者が同じ基準で評価します。

試行で確認する観点と記録
観点確認する内容残す記録
根拠との整合主要な主張を証拠で追えるか。裏付けのない断定がないか根拠付き主張と確認対象主張の数、誤りの内容
分析の深さ直接原因・流入・流出を区別し、代替仮説を検討したか評価理由、見落とし、確認者間の不一致
改善への接続原因に対応する対策と効果確認方法があるか対策の実施・効果、類似不具合の再発
開発者の負担必要な背景を引き出せ、修正や復旧を妨げないか対話時間、質問数、訂正内容、回答しやすさ
評価の注意
承認率の高さだけでは正しさを証明できません。再発件数も変更規模・検証・利用状況に左右されるため、AI単独の効果と断定しません。試行で基準と負担を確認してから適用範囲を広げます。
08 / FIRST RELEASE

最初は、分析案を作るところまで。

入力と出力

入力：不具合票、修正差分、関連コード、当時の仕様、テスト結果、開発者との対話。

出力：根拠付き分析案、未確認事項、原因に対応した対策案、人による確認履歴。品質台帳へ転記できる形式で提供します。

初期導入の境界

自動修正・自動原因確定・個人の採点は対象に含めません。最初は手動で資料を渡し、対話と分析記録の有用性を検証します。

連携先、モデル、実行環境、保存先、費用、運用責任者は導入時に決定します。

この取り組みが残したいもの

不具合の分類だけでなく、「どういう条件が実装を生み、なぜ検知できず、何を変えると防げるか」を、次の開発で使える形にした学習の記録です。
